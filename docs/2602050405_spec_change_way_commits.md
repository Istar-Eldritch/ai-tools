# Agent-Based Commit Strategy

**Status**: Draft  
**Created**: 2026-02-05

## PART I: Requirements

### Problem Statement

**Business context**: The spec-pipeline extension currently uses checkpoint commits as a rollback mechanism before agents modify files. These checkpoints create noisy git history with generic messages like `[CHECKPOINT] Before implementer - Phase 1, Cycle 1`, which don't convey what work was accomplished. This makes it difficult to understand the pipeline's progress by reviewing git history, and requires users to manually interpret checkpoint patterns.

**Current state**: 
- Checkpoint commits are created *before* write operations (specDrafter, planDrafter, implementer, addressReview)
- Meaningful commits are only created *after* spec approval and phase completion
- Checkpoint commits serve two purposes: (1) rollback points for error recovery, and (2) markers for squash merge functionality
- Git history contains many checkpoint commits interspersed with a few meaningful commits
- The `state.checkpoints[]` array tracks checkpoint commit hashes for squashing

**Key issues**:
1. **Poor git history legibility**: Checkpoints dominate the history but carry no semantic information
2. **Delayed context**: Meaningful commits only appear after full phases complete, losing granular progress tracking
3. **Manual interpretation required**: Users must mentally map checkpoints to actual work done
4. **Missed addressReview commits**: When review fixes are applied, only a checkpoint exists—no commit message describes what issues were addressed

### Requirements

**R1**: Replace checkpoint commits with meaningful commits created *after* agents successfully complete their work and modify files.

**R2**: The following agent roles should trigger commits after successful file modifications:
- `specDrafter`: After drafting or redrafting specs
- `planDrafter`: After drafting phase plans
- `implementer`: After initial implementation
- `addressReview`: After applying review fixes

**R3**: The `discoveryAgent` should NOT trigger commits (it only creates discovery metadata, not implementation artifacts).

**R4**: Each commit message should be generated by a specialized agent receiving the following context:
- **Agent role and model**: Which agent ran (e.g., "specDrafter") and which model was used (e.g., "opus")
- **Review feedback**: If the commit follows a review cycle, include the review output that was addressed
- **Phase and cycle**: If in implementation stage, include phase number (1-indexed) and cycle number (1-indexed)
- **Files modified**: List of files changed by the agent (obtained via `git diff --name-only`)

**R5**: The commit message generation agent configuration should be:
- **Configurable**: Add `agentCommitMessageWriter` key to `models` configuration with `ModelConfig` type
- **Default model**: `haiku` with `thinking: off` for speed and cost efficiency
- **Independent from old commitMessageWriter**: The existing `commitMessageWriter` (used for phase-level commits after all review cycles) remains fixed at haiku/off and is NOT configurable

**R6**: Error handling for agent execution:
- **Success path**: After an agent exits with code 0 and modifies files, create a commit
- **Failure path**: After an agent exits with code ≠ 0, run `git stash push -m "spec-pipeline-error-{timestamp}" --include-untracked` to preserve dirty state
- **Recovery mechanism**: Use `git reset --hard HEAD` to restore clean state (no checkpoint needed—current HEAD is the recovery point)
- **Stash cleanup**: Drop the error stash after a successful retry

**R7**: Commit message generation with retry and fallback:
- **Retry policy**: Use exponential backoff with 3 attempts total (1 initial + 2 retries)
- **Backoff parameters**: 1 second initial delay, 2x multiplier (delays: 1s, 2s)
- **Fallback format**: If all retries fail, use: `[FALLBACK] After {role} - Phase {phase}, Cycle {cycle} - {fileCount} files modified`
- **Abort on fallback**: When fallback is used, log an error and abort the pipeline (user must resume)

**R8**: Only stage files that the agent modified:
- **File detection**: Run `git diff --name-only` after agent completes to get modified file list
- **Staging command**: Use `git add --all <file>...` to handle modifications, deletions, and renames
- **Empty changes**: If `git diff --staged --quiet` shows no staged changes after staging, skip the commit (no empty commits)

**R9**: Spec and plan redrafting behavior:
- **No amending**: When a spec or plan is rejected during user approval and the drafter re-runs, create a *new* commit (not amend)
- **Iteration tracking**: Each redraft gets its own commit, preserving the revision history

**R10**: Implementation commit granularity:
- **Initial implementation**: Commit after the `implementer` role completes (before code review starts)
- **Review fixes**: Commit after each `addressReview` role completes (one commit per fix cycle, not bundled)
- **Rationale**: This provides granular tracking of fix iterations without bundling unrelated changes

**R11**: Backward compatibility and rollout:
- **Applies to new pipelines only**: The new commit strategy activates for pipelines created after this feature ships
- **Existing pipelines unaffected**: In-progress pipelines continue using checkpoints (no migration required)
- **No version flag needed**: Behavior is implicitly determined by when the pipeline was created

**R12**: Squash merge compatibility:
- **Track agent commits**: Add agent commit hashes to the existing `state.checkpoints[]` array
- **Existing squash logic**: The `squashCheckpointCommits()` function treats agent commits identically to old checkpoint commits
- **No refactoring required**: Reusing `checkpoints[]` avoids changes to squash/merge workflows

**R13**: Stash lifecycle after retry:
- **Drop after success**: When a retry succeeds, drop the error stash using `git stash drop {stashRef}`
- **Keep on failure**: If retry fails, preserve the stash for manual recovery
- **Defensive check**: Before dropping, verify stash still exists with `git stash show {stashRef}`

### Success Criteria

- [ ] Checkpoint commits are no longer created before write operations
- [ ] Commits are created after specDrafter, planDrafter, implementer, and addressReview complete successfully
- [ ] discoveryAgent does NOT trigger commits
- [ ] Commit messages include context: role, model, phase, cycle, files modified
- [ ] agentCommitMessageWriter is configurable in the models section
- [ ] Old commitMessageWriter remains fixed at haiku/off
- [ ] Agent failures trigger stashing with identifiable messages
- [ ] Commit message generation retries 3 times with exponential backoff
- [ ] Fallback commit message includes contextual information
- [ ] Pipeline aborts when fallback message is used
- [ ] Only files modified by the agent are staged
- [ ] Empty commits are skipped (no changes = no commit)
- [ ] Spec/plan redrafts create new commits (no amending)
- [ ] Initial implementation and each addressReview fix get separate commits
- [ ] Agent commit hashes are added to state.checkpoints[]
- [ ] Squash merge functionality continues to work unchanged
- [ ] Error stash is dropped after successful retry
- [ ] Existing pipelines continue using checkpoints
- [ ] New pipelines use the new commit strategy
- [ ] All existing tests pass
- [ ] Git history shows meaningful commit messages instead of checkpoints

### Out of Scope

- **Discovery commits**: The `discoveryAgent` will not trigger commits
- **Commit message templates**: No user-customizable commit message formats
- **Interactive commit editing**: Users cannot edit commit messages before they're created
- **Amend behavior for redrafts**: Always create new commits, never amend
- **Automatic squashing**: Users still choose when to squash via explicit commands
- **Checkpoint removal from old pipelines**: Existing pipelines keep using checkpoints
- **Commit signing**: No GPG signing or commit verification
- **Commit message validation**: No enforcement of conventional commit formats

### Architectural Guidance

**Modified Modules**:
- `git.ts`: Add new functions for file tracking, selective staging, and agent commit creation
- `agents.ts` or new `commit-agent.ts`: Implement commit message generation with retry/fallback
- `pipeline.ts`: Replace checkpoint calls with agent commit calls after write operations
- `review.ts`: Add commits after addressReview operations
- `types.ts`: Add `agentCommitMessageWriter` to config schema
- `config.ts`: Add default config for `agentCommitMessageWriter`
- `errors.ts`: Update error handling to use stashing instead of checkpoints

**Key Design Decisions**:

1. **File Tracking Approach** (Phase 1):
   - Capture dirty state before agent runs using `git status --porcelain`
   - After agent completes, run `git diff --name-only` to identify modified files
   - This avoids complex write monitoring and handles all git operations (modify, delete, rename)

2. **Commit Agent Integration** (Phase 2):
   - Create a dedicated `generateCommitMessage()` function with retry logic
   - Return a `Result<string, 'fallback'>` type to distinguish success/fallback cases
   - Use the existing `runAgentWithConfig()` infrastructure for consistency

3. **Pipeline Integration Pattern** (Phase 3):
   - Replace all `createCheckpointAndSave()` calls with a new `createAgentCommit()` function
   - The new function should:
     1. Check if files were modified
     2. Generate commit message
     3. Stage modified files
     4. Create the commit
     5. Add commit hash to `state.checkpoints[]`
   - Apply this pattern uniformly across spec drafting, plan drafting, and implementation stages

4. **Error Recovery Flow** (Phase 4):
   - When agent fails: stash → save error state → notify user
   - When user resumes: offer retry → run agent → on success: drop stash + create commit
   - The stash serves the same purpose as the old checkpoint but without polluting history

5. **Backward Compatibility** (Phase 5):
   - No state migration needed—new behavior applies to new pipelines only
   - The `checkpoints[]` array serves double duty: checkpoints for old pipelines, agent commits for new ones
   - Squash logic remains unchanged because it operates on `checkpoints[]` regardless of commit type

**Testing Strategy**:
- Unit tests for git utilities (file tracking, selective staging)
- Unit tests for commit message generation with retry/fallback
- Integration tests for pipeline stages creating commits
- Manual testing of error recovery flow (agent failure → stash → retry → commit)
- Regression testing of squash merge functionality
