# Discovery-to-Implementation Flow for /implement Command

**Status**: Draft
**Created**: 2026-02-11
**Spec ID**: 2602111351

---

## PART I: Requirements

### 1. Problem Statement

#### Business Context

The spec pipeline currently supports two main workflows: (1) `/spec` for conversational discovery → spec drafting → approval, and (2) `/implement` for taking a completed spec file through plan→code→review cycles. For small-to-medium changes where a full formal spec is overkill, users must either skip discovery entirely (`/implement --no-plan --no-review spec.md`) or go through the full spec creation workflow just to feed the result into `/implement`.

There is a missing middle ground: using the discovery agent to refine and scope a request through natural conversation, then feeding that context directly into implementation — without the overhead of formal spec drafting, approval, and review stages.

#### Current State

**Existing Workflows:**

1. **`/spec <description>`** — Enters conversational discovery (host LLM explores codebase, proposes assumptions one at a time). After `/spec-done`, transitions to spec drafting mode. After `/spec-draft-done`, user approves. The spec file is saved to `specsDir`.

2. **`/implement <spec-path>`** — Requires a spec file on disk. Reads content, extracts phases from a phase table, and runs the plan→implement→review pipeline per phase. Supports `--no-plan` to skip plan generation and `--no-review` to skip reviews.

3. **`/plan <description>`** — Ephemeral scoping conversation (not persisted). Recommends roadmap/epic/feature level.

**Discovery Infrastructure:**
- Discovery runs via `before_agent_start` prompt injection, turning the host LLM into a discovery agent
- Conversation history tracked in `ConversationalPipelineState.discovery.conversationHistory`
- Summary generated by `generateConversationalDiscoverySummary()` in `state.ts`
- Two separate discovery-done commands exist: `/spec-done` (for spec discovery) and `/discovery-done` (for hierarchy discovery)
- `activePipelineKind` variable routes behavior: `"spec"` | `"hierarchy"`

**Key Limitation:**
- `/implement` only accepts a file path — there is no way to enter discovery mode and feed the result directly into implementation
- Discovery prompt functions are tightly coupled to `SpecState` and `HierarchyState` types, even though they only use `ConversationalPipelineState` fields

#### Key Issues

| ID | Issue | Impact |
|----|-------|--------|
| I1 | No discovery→implement path | Users must create a full spec for small changes that benefit from codebase exploration |
| I2 | Two separate discovery-done commands | Confusing UX — `/spec-done` for specs, `/discovery-done` for hierarchy |
| I3 | Discovery prompts coupled to specific state types | Cannot reuse discovery infrastructure for new pipeline kinds without duplication |

### 2. Requirements

#### New Discovery Mode for /implement

**R1**: The `/implement` command MUST accept a text description (not a file path) as an alternative to a spec file path.

**R2**: When the argument does not resolve to an existing file on disk, the command MUST enter conversational discovery mode instead of showing a "file not found" error.

**R3**: When the argument looks like a misspelled file path (contains `/` or ends with a file extension like `.md`, `.typ`), the command MUST show a "file not found" error — not enter discovery mode.

**R4**: During implement-discovery mode, the host LLM MUST behave identically to spec discovery — exploring the codebase, proposing assumptions one at a time, and allowing the user to confirm or correct.

**R5**: The discovery prompt MUST tell the user to type `/discovery-done` to proceed to implementation (not to spec drafting).

**R6**: When `/discovery-done` is triggered during implement-discovery:
  - The discovery summary MUST be generated from conversation history using `generateConversationalDiscoverySummary()`
  - The summary MUST be written to a file in `specsDir` with naming convention `{timestamp}_discovery_{shortname}.md`
  - The file path and content MUST be passed to the existing `createInitialImplState()` and `runImplementPipeline()` — the implementation pipeline receives it as a normal "spec"

**R7**: The `--no-plan` and `--no-review` flags MUST be parsed at `/implement` invocation time and carried through to the implementation pipeline after discovery completes.

**R8**: The user MUST be prompted for a short name (via `promptForShortName()`) at `/implement <description>` invocation time, consistent with `/spec`, `/roadmap`, and `/epic`.

#### Unified /discovery-done Command

**R9**: The `/discovery-done` command MUST be the single command for completing discovery across ALL pipeline kinds (spec, hierarchy, and implement).

**R10**: The `/discovery-done` handler MUST dispatch based on `activePipelineKind`:
  - `"spec"` → call `endDiscoveryAndStartDrafting()` (current `/spec-done` behavior)
  - `"hierarchy"` → run hierarchy discovery→drafting transition (current `/discovery-done` behavior)
  - `"implement"` → write discovery summary file, check git clean, launch implement pipeline

**R11**: The `/spec-done` command MUST be removed entirely. All spec discovery prompts and documentation MUST be updated to reference `/discovery-done`.

**R12**: All discovery mode prompts (spec, hierarchy, implement) MUST consistently tell the user to type `/discovery-done`.

#### Lightweight State Management

**R13**: The implement-discovery session MUST use a plain `ConversationalPipelineState` object (`{ id, description, discovery }`) — not `SpecState` or any new persisted type.

**R14**: The implement-discovery state MUST be ephemeral (in-memory only) — not persisted to disk. If cancelled, the conversation is lost.

**R15**: The `activePipelineKind` union type MUST be extended to include `"implement"`: `"spec" | "hierarchy" | "implement"`.

**R16**: A new `enterImplementDiscoveryMode()` function MUST be created (or the existing enter functions extended) to set `activePipelineKind = "implement"` and configure the state machine for implement-discovery.

#### Deferred Git Clean Check

**R17**: When `/implement <description>` enters discovery mode, it MUST validate that a git repo exists but MUST NOT check for a clean working tree.

**R18**: The git clean check MUST happen at `/discovery-done` transition time (before writing the summary file and launching the pipeline).

**R19**: If the working tree is dirty at `/discovery-done` time, the command MUST show the "uncommitted changes" error. The discovery state MUST be preserved in memory so the user can stash/commit and re-trigger `/discovery-done`.

#### Cancellation

**R20**: `/implement-cancel` MUST handle both phases:
  - During discovery (`pipelineMode === "discovery" && activePipelineKind === "implement"`): call `exitMode()`, clear widget, show "Discovery cancelled."
  - During implementation (existing persisted `ImplementationState`): existing cancel behavior unchanged

**R21**: The discovery-phase cancel MUST follow the same pattern as `/plan-cancel` — ephemeral state, no persistence, no cleanup.

#### Unified Discovery Prompt

**R22**: The `buildDiscoveryPromptInjection` function MUST be refactored to accept `ConversationalPipelineState` (instead of `SpecState`) with configurable parameters:
  - `doneCommand`: string (e.g., `"/discovery-done"`)
  - `sessionLabel`: string (e.g., `"Implementation"`, `"Spec"`, `"Roadmap"`)
  - `nextStep`: string (e.g., `"proceed to implementation"`, `"proceed to spec drafting"`)

**R23**: The `buildHierarchyDiscoveryPromptInjection` function MUST be consolidated into the unified `buildDiscoveryPromptInjection` — accepting optional `parentContext` parameter to cover hierarchy-specific needs.

**R24**: The `before_agent_start` handler MUST use the unified function for all three pipeline kinds, passing the appropriate parameters.

### 3. Success Criteria

- [ ] `/implement "Add user auth"` enters discovery mode (conversational, host LLM proposes assumptions)
- [ ] `/implement docs/my_spec.md` works as before (reads file, implements)
- [ ] `/implement docs/nonexistent.md` shows "file not found" error (not discovery mode)
- [ ] `/implement --no-plan --no-review "Fix the login bug"` enters discovery, then implements without plan or review
- [ ] `/discovery-done` during implement-discovery writes summary file and launches implementation
- [ ] `/discovery-done` during spec-discovery transitions to drafting (same as old `/spec-done`)
- [ ] `/discovery-done` during hierarchy-discovery transitions to hierarchy drafting (unchanged)
- [ ] `/spec-done` command no longer exists
- [ ] `/implement-cancel` during discovery exits cleanly with "Discovery cancelled"
- [ ] `/implement-cancel` during implementation works as before
- [ ] Git dirty tree check happens at `/discovery-done` time, not at `/implement` invocation
- [ ] Discovery summary file written to `specsDir` with `{timestamp}_discovery_{shortname}.md` naming
- [ ] All existing tests pass (337 tests, no changes to `implement-pipeline.ts`)

### 4. Out of Scope

- Persisting implement-discovery state to disk (resumability) — can be added later
- New `/implement-resume` behavior for the discovery phase — discovery is ephemeral
- Changes to `implement-pipeline.ts` — the pipeline receives the discovery file as a normal spec
- Changes to `ImplementationState` type — no new fields needed
- Adding discovery mode to other commands beyond `/implement`
- Multi-phase extraction from discovery summaries — always falls through to single-phase fallback

### 5. Open Questions

None — all ambiguities were resolved during discovery.

## PART II: High-Level Implementation Plan

### Implementation Approach

This feature has three logical areas of change: (1) extending `/implement` to detect and enter discovery mode, (2) unifying the `/discovery-done` command to dispatch across all pipeline kinds, and (3) refactoring the discovery prompt system into a single configurable function. All changes are in `extensions/spec-pipeline/index.ts` with no modifications to `implement-pipeline.ts`, `types.ts`, or `state.ts`.

### Phase Overview

| Phase | Focus | Effort |
|-------|-------|--------|
| Phase 1 | Unified discovery prompt function and `/discovery-done` consolidation | 1 day |
| Phase 2 | Implement discovery mode for `/implement` command | 1 day |
| Phase 3 | Cancellation, widget updates, and documentation | 0.5 days |

### High-Level Guidance

**Phase 1 — Unified Discovery Prompt & /discovery-done:**
- Refactor `buildDiscoveryPromptInjection` to accept `ConversationalPipelineState` + config params (`doneCommand`, `sessionLabel`, `nextStep`, optional `parentContext`)
- Remove `buildHierarchyDiscoveryPromptInjection` — fold its parent context logic into the unified function
- Update `before_agent_start` handler to use the unified function for both `"spec"` and `"hierarchy"` kinds
- Extend `/discovery-done` handler to also dispatch `activePipelineKind === "spec"` (absorbing `/spec-done` logic)
- Remove `/spec-done` command registration
- Update all discovery prompt strings to say `/discovery-done` instead of `/spec-done`
- Extend `activePipelineKind` type to `"spec" | "hierarchy" | "implement"`

**Phase 2 — /implement Discovery Mode:**
- Modify `/implement` handler: after stripping flags, check `fs.existsSync()` on the remaining arg
- Add path-like heuristic: if arg contains `/` or ends with `.md`/`.typ`, show "file not found" error
- If not a file and not path-like: enter discovery mode
  - Call `promptForShortName()` and `generateTimestamp()` at invocation
  - Create ephemeral `ConversationalPipelineState` with discovery state
  - Create `enterImplementDiscoveryMode()` function that sets `activePipelineKind = "implement"`, `pipelineMode = "discovery"`
  - Store `--no-plan` and `--no-review` flags for later use (module-level variables or closure)
  - Validate git repo exists (but skip clean check)
- Add `"implement"` branch in unified `/discovery-done`:
  - Check git clean
  - Generate discovery summary, write to `{specsDir}/{timestamp}_discovery_{shortname}.md`
  - Read file content, call `createInitialImplState()`, apply flags, call `runImplementPipeline()`
  - Exit discovery mode

**Phase 3 — Cancellation, Widgets & Docs:**
- Modify `/implement-cancel` to check `pipelineMode === "discovery" && activePipelineKind === "implement"` first
- Update `updateModeWidget()` to handle `activePipelineKind === "implement"` in discovery mode
- Update README.md documentation: new `/implement <description>` usage, unified `/discovery-done`, removal of `/spec-done`
- Update command description strings and header comments in `index.ts`

**Patterns to Follow:**
- `/plan` command's ephemeral `ScopingState` pattern for the implement-discovery state
- `/plan-cancel` pattern for discovery-phase cancellation in `/implement-cancel`
- Existing `--no-plan` flag parsing pattern for carrying flags through discovery
- `enterScopingMode()` pattern for the new `enterImplementDiscoveryMode()` function

**Testing Approach:**
- Existing 337 tests should all pass unchanged (no modifications to `implement-pipeline.ts`, `state.ts`, `types.ts`, `review.ts`, etc.)
- Manual testing: `/implement <description>` flow, `/implement <file>` unchanged, flag combinations, cancel during discovery, dirty tree at `/discovery-done`, path-like heuristic
