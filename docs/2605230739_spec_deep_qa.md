# Spec: Per-Topic Drill-Down Threads in Extension-Driven Discovery

**Status:** Draft
**Created:** 2026-05-23
**Timestamp:** 2605230739

## Problem Statement

- **Business context:** The `/spec` extension-driven discovery loop asks one clarifying question at a time and treats any non-command reply as the final answer to that topic. Real requirement discovery is iterative — users often need to ask follow-up questions about a topic before they can confirm or correct the assumption.
- **Current state:** `index.ts` stores one `pendingDiscoveryQuestion`, treats the first user reply as the definitive answer, records it in `discoveryQAPairs` as a closed `{ question, answer }` pair, and immediately calls the next `runDiscoveryStep`. There is no way to continue exploring a topic without abandoning it.
- **Key issues:**
  1. Users cannot ask clarifying questions about a subagent assumption before committing to an answer.
  2. Exploratory follow-up replies are persisted as if they were settled decisions (flat `Q/A` pairs).
  3. In-progress topic threads are lost on `/spec-resume` because `pendingDiscoveryQuestion` and `discoveryQAPairs` are module-local variables, never persisted to `DiscoveryState`.
  4. `generateConversationalDiscoverySummary` renders all exchanges as equal-weight `### Exchange N` blocks; multi-turn threads would appear as separate decisions rather than a single settled topic with supporting context.

## Requirements

- **R1.** While a discovery topic is pending (`pendingDiscoveryQuestion !== null`), the extension must classify each user reply as either a **follow-up question** or a **final decision** before acting on it.
- **R2.** If a reply is classified as a follow-up, the extension must call the discovery subagent in the context of the active topic thread and append both the follow-up question and the subagent's answer to that thread. `pendingDiscoveryQuestion` stays set (topic remains open).
- **R3.** If a reply is classified as a final decision (confirmation or correction), the active topic thread is closed, stored in `discoveryQAPairs`, and the next `runDiscoveryStep` is triggered.
- **R4.** Classification must be model-based (no new slash commands or UI prefixes), matching the existing natural-language UX.
- **R5.** The active topic thread (original question + all follow-up exchanges) must be persisted to `DiscoveryState` after each follow-up so that `/spec-resume` can restore the in-progress thread.
- **R6.** Completed topic threads must be rendered distinctly in the discovery summary passed to the spec drafter: the settled decision is the primary signal; follow-up exchanges appear as supporting context under that topic.
- **R7.** The feature is scoped to the extension-driven `/spec` discovery loop only (`discoveryLoopActive === true`). Hierarchy (`/roadmap`, `/epic`) and implement-discovery flows are unaffected.
- **R8.** Existing behaviour when the user sends a one-shot confirmation ("yes", "sounds good") must be unchanged — no extra latency from classification when the reply is unambiguously a decision.

## Success Criteria

- [ ] A user can type multiple questions in response to a subagent assumption; each follow-up triggers a subagent reply on the same topic without advancing to the next question.
- [ ] The conversation does not advance to the next discovery topic until the user sends a reply the classifier considers a decision.
- [ ] Resuming a spec mid-topic via `/spec-resume` restores the active thread and continues on the same question.
- [ ] The discovery summary fed to the spec drafter shows each topic as a block with the decision first and follow-up context nested under it; no follow-up question appears as a standalone settled decision.
- [ ] `/discovery-done` exits correctly even when a topic thread is in progress, flushing the partial thread as a single entry.
- [ ] No new slash commands or typed prefixes are required.

## Out of Scope

- Drill-down threads for hierarchy (`/roadmap`, `/epic`) or implement-discovery flows.
- UI beyond `ctx.ui.notify` (no inline chat widget, no separate panel).
- Automatic topic closure after N follow-ups (the loop runs until the classifier sees a decision or the user types `/discovery-done`).

## Open Questions

- [ ] Classification latency: calling the discovery model per reply adds a round-trip before showing the next subagent answer. Should we optimistically assume short single-word replies are decisions and skip the classifier, falling back only for ambiguous text?

## Implementation Plan

The pipeline parses the table below to drive `/implement`.

| Phase | Focus | Effort |
|-------|-------|--------|
| Phase 1 | Type changes: `DiscoveryTopic` type + update `DiscoveryState` to persist active topic thread | 0.5 days |
| Phase 2 | Classifier subagent call in the `input` handler — model-based follow-up vs decision detection | 1 day |
| Phase 3 | Follow-up subagent call (`runFollowUpStep`) that keeps `pendingDiscoveryQuestion` active | 0.5 days |
| Phase 4 | `generateConversationalDiscoverySummary` update — per-topic sections with decision + supporting thread | 0.5 days |
| Phase 5 | `/spec-resume` restore: reload active topic thread from `DiscoveryState` into module-local vars | 0.5 days |

### Phase 1: Type changes

`DiscoveryTopic` is a new type that models one complete or in-progress topic:

```ts
// types.ts
export interface DiscoveryFollowUp {
  userQuestion: string;
  agentAnswer: string;
  timestamp: string;
}

export interface DiscoveryTopic {
  /** The original subagent assumption/question */
  question: string;
  /** Follow-up exchanges within this topic (empty for one-shot answers) */
  followUps: DiscoveryFollowUp[];
  /** The user's final confirmation or correction. Null while thread is open. */
  decision: string | null;
  timestamp: string;
}
```

`DiscoveryState` gains two new optional fields (both optional so existing persisted states deserialise without migration):

```ts
export interface DiscoveryState {
  skipped: boolean;
  discoverySummary: string;
  completed: boolean;
  conversationHistory?: ConversationalExchange[]; // kept for legacy summary path
  /** Closed topics from the extension-driven loop */
  topics?: DiscoveryTopic[];
  /** In-progress topic thread (null when no topic is pending) */
  activeTopic?: DiscoveryTopic | null;
}
```

Module-local state in `index.ts` changes:

```ts
// BEFORE
let discoveryQAPairs: Array<{ question: string; answer: string }> = [];
let pendingDiscoveryQuestion: string | null = null;

// AFTER
let discoveryTopics: DiscoveryTopic[] = [];       // closed topics
let activeDiscoveryTopic: DiscoveryTopic | null = null;  // replaces pendingDiscoveryQuestion
```

`pendingDiscoveryQuestion` is removed; callers check `activeDiscoveryTopic !== null` instead.

### Phase 2: Classifier subagent call

When the `input` handler captures a reply while `activeDiscoveryTopic !== null`, it calls a lightweight classifier before deciding what to do:

```ts
async function classifyDiscoveryReply(
  reply: string,
  topic: DiscoveryTopic,
  projectConfig: ProjectConfig,
  cwd: string,
  signal: AbortSignal,
): Promise<"followup" | "decision"> { ... }
```

System prompt (minimal, fast model — `agentCommitMessageWriter` or similar):

```
You are classifying a user reply during requirements discovery.
The active topic is: "<topic.question>"
The user replied: "<reply>"
Output exactly one word: FOLLOWUP or DECISION.
- FOLLOWUP: the reply asks a question or requests more information about this topic.
- DECISION: the reply confirms, corrects, or closes the topic (even partially).
```

If the classifier fails or the reply is a single word ("yes", "no", "ok", "sure") skip the call and treat it as a DECISION directly (R8 optimisation).

### Phase 3: Follow-up subagent call (`runFollowUpStep`)

When the classifier returns FOLLOWUP:

1. Append `{ userQuestion: reply, agentAnswer: "", timestamp }` placeholder to `activeDiscoveryTopic.followUps`.
2. Persist `state.discovery.activeTopic = activeDiscoveryTopic` to disk.
3. Call `runAgentWithConfig` with a system prompt that includes:
   - The original topic question
   - All previous follow-ups in the thread
   - Instruction: answer this one follow-up question in the context of the topic; do NOT advance to a new topic.
4. Fill in `agentAnswer`, persist again.
5. Display answer via `ctx.ui.notify`.
6. Return `{ action: "handled" }` — host agent does not run.

When the classifier returns DECISION:

1. Set `activeDiscoveryTopic.decision = reply`.
2. Push to `discoveryTopics`. Clear `activeDiscoveryTopic`.
3. Persist `state.discovery.topics`, clear `state.discovery.activeTopic`.
4. Call `runDiscoveryStep` for next topic (existing flow).

### Phase 4: Summary generation

`generateConversationalDiscoverySummary` receives `DiscoveryTopic[]` instead of (or in addition to) flat `ConversationalExchange[]`. New rendering:

```
## Discovery Summary

### Topic 1: <first ~12 words of question>

**Assumption:** <full question text>

**Decision:** <user's final confirmation/correction>

<if followUps.length > 0>
**Supporting thread:**
- Q: <followUp.userQuestion>
  A: <followUp.agentAnswer>
...
```

The existing `ConversationalExchange[]`-based path is kept as a fallback so legacy states (pre-feature) still render correctly.

### Phase 5: `/spec-resume` restore

When `/spec-resume` reloads a `SpecState` with `stage === "discovery"`:

1. If `state.discovery.activeTopic` is non-null, restore it into `activeDiscoveryTopic`.
2. Restore `state.discovery.topics ?? []` into `discoveryTopics`.
3. Set `discoveryLoopActive = true` and re-enter discovery mode.
4. Notify the user: "Resuming topic: `<activeTopic.question.slice(0, 80)>…`" then display the question again via `ctx.ui.notify` so they can continue answering.

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Classifier latency adds noticeable delay before follow-up answers | Skip classifier for short/unambiguous replies (single word, starts with "yes"/"no"); display "🤔 Checking…" notify while classifier runs |
| Classifier misclassifies a decision as a follow-up, leaving topic open indefinitely | User can always type `/discovery-done` to flush and move on; add "Type /discovery-done to close this topic" hint after 3+ follow-ups |
| `activeTopic` persisted but `runFollowUpStep` subagent call is in-flight on crash | On resume, if `activeTopic` has an empty-string `agentAnswer` in the last followUp, drop that placeholder and re-ask |
