## Problem Statement

- **Business context:** pi sessions accumulate rich conversational context — decisions, code patterns, architectural choices, bug fixes — but this context is lost when sessions end or when switching between projects. The existing `pi-hermes-memory` extension provides memory capabilities, but uses SQLite + HRR vectors (poor semantic retrieval), requires manual `memory` tool calls, and bundles ~15 features (session search, skill injection, correction detection, background learning loops) that create maintenance overhead and confuse the agent about when to use which tool.
- **Current state:** `pi-hermes-memory` is installed at `~/.pi/agent/pi-hermes-memory/`. It registers `memory_search`, a manual `memory` CRUD tool, `session_search`, `skill` tools, and a dozen slash commands. The current `extensions/huginn/package.json` lists `postgres` and `openai` as dependencies, but the intended stack is zero-infra (PGlite + local ONNX embeddings).
- **Key issues:**
  1. No automatic ingestion — agent must manually decide to store memories
  2. Weak semantic retrieval — HRR vectors approximate but do not rank by true cosine similarity
  3. External API dependency — OpenAI embeddings cost money and require API keys
  4. External server dependency — Postgres server required for pgvector
  5. Feature bloat — ~15 capabilities spread across tools, commands, and background loops create a confusing surface area
  6. No codebase awareness — agent cannot search current project source files semantically without running the separate Rust RAG MCP server

## Requirements

- **R1. In-process, zero-infra stack**  
  Use PGlite (`@electric-sql/pglite`) with bundled pgvector for storage and local ONNX embeddings via `@huggingface/transformers` (`nomic-embed-text-v1.5`). No running Postgres server, no OpenAI API calls, no network dependencies after first model download.

- **R2. Unified single-table schema with source-type discriminator**  
  Store both conversation chunks and codebase chunks in one `huginn_chunks` table with a `source_type` discriminator (`conversation` | `codebase`). Schema includes: `source_type`, nullable `role` (conversation only), `session_id` (conversation only), `source_file`, `start_line`, `end_line`, `file_mtime`, `file_size` (codebase provenance and invalidation). Drop the globally-unique `content_hash` constraint; use `UNIQUE (session_id, content_hash, chunk_index)` for conversation dedup only. Codebase chunks rely on file-level deletion/re-insertion for dedup.

- **R3. Automatic conversation ingestion on `message_end`**  
  Listen on `message_end` (not `turn_end`) for all configurable roles. Filter by `event.message.role` against `ingestRoles` (default `['user', 'assistant', 'toolResult']`). For each matching message: detect content type → chunk → embed → upsert. Fire-and-forget with error logging only; never block the UI.

- **R4. Automatic codebase indexing in the background**  
  On `session_start`: trigger a background scan of the current working directory. Use `git ls-files --cached --others --exclude-standard` when inside a git repo (respects `.gitignore`, global gitignore, and `.git/info/exclude`). Fall back to manual directory crawling with `.gitignore` + global gitignore parsing when git is unavailable. Layer hardcoded exclusions on top: `.git/`, `.pi-lens/`, `node_modules/`, `target/`, `.next/`, `dist/`, lockfiles, files > 1MB. Ignore dot-directories by default (e.g. `.husky/`, `.turbo/`) but keep individual dotfiles (e.g. `.github/workflows/*.yml`). Periodically re-scan (30-second interval or `fs.watch`/`chokidar`) to detect new/changed/deleted files. On file change: delete all old chunks for that `(project, source_file)` then re-chunk and re-embed. On file deletion: remove all chunks for that path as orphans.

- **R5. Dual chunking strategy**  
  **Conversations:** Lightweight pure-JS chunker splitting on markdown headings, paragraph boundaries, and code fences. No AST parsing — conversation messages carry no reliable filename metadata. **Codebase files:** Tree-sitter AST-aware chunking for `.ts`, `.tsx`, `.py`, `.rs`, `.java` (and any other languages whose grammar packages are installed). Extract top-level nodes (functions, classes, impl blocks, methods) with parent context. Overflow large nodes into char-based sub-chunks. Tree-sitter packages are listed in `dependencies` for install convenience, but huginn loads them dynamically via `await import()` wrapped in try-catch. If loading fails (e.g. `node-gyp` build failure on ARM/Windows), huginn gracefully degrades to lightweight JS chunking for code files.

- **R6. Auto-retrieval prefetch on `message_end` (user)**  
  On `message_end` where `event.message.role === 'user'`: embed the user's prompt text, run `huginn_memory_search` asynchronously, store the prefetched results in a transient `prefetchedBlock`. Show a UI widget (via `ctx.ui.setWidget`) while prefetching. On the subsequent `context` event — before the first LLM call for this user message — inject the prefetched block as `<huginn-context>...</huginn-context>` appended to the last user message, then clear `prefetchedBlock` so it is not injected again on later `context` events within the same turn (e.g. after tool calls).

- **R7. Single `huginn_memory_search` tool for retrieval**  
  Register exactly one tool named `huginn_memory_search` (replaces the identically-named tool from `pi-hermes-memory`; user must uninstall `pi-hermes-memory` to avoid collision). Signature: `huginn_memory_search(query: string, project?: string, limit?: number, source_type?: 'conversation' | 'codebase' | 'all')`. **Default search behavior:** return conversation chunks from all projects, and codebase chunks filtered to the current project only (i.e. implicit `WHERE (source_type = 'conversation') OR (source_type = 'codebase' AND project = $currentProject)`). User can override with explicit `project` or `source_type` filters.

- **R8. Configurable via `.pi/huginn.json`**  
  Resolve config from `.pi/huginn.json` merged with sensible defaults. Keys: `dataDir`, `embeddingModel`, `embeddingDim`, `chunkSize`, `chunkOverlap`, `minChunkSize`, `autoIngestion`, `ingestRoles`, `autoRetrieval`, `autoRetrievalMax`, `minSimilarity`, `reindexBatchSize`, `extraIgnore`, `ignoreDotDirs` (default `true`).

- **R9. Embedding model swappability with reindex command**  
  Store `embedding_model` and `embedding_dim` in a single-row `huginn_config` table. On startup, compare current model against stored config; if mismatch, log warning and disable auto-retrieval until reindex. Provide `/huginn-reindex` command to re-embed all chunks in batches (default 32). If new model has different dimensions, alter vector column type and recreate HNSW index.

- **R10. Commands**  
  - `/huginn-reindex [--model <name>]` — Re-embed all chunks (conversation + codebase)
  - `/huginn-status` — Show indexed counts (conversations vs codebase), current model, last scan time

- **R11. No migration from pi-hermes-memory for v1**  
  Huginn starts empty on first install and accumulates memory organically per session. A future one-time import command may read `pi-hermes-memory`'s SQLite memories, but this is out of scope for v1.

- **R12. Clean lifecycle**  
  `session_start` → init PGlite, ensure schema, check model mismatch, trigger background codebase scan. `session_shutdown` → close PGlite cleanly, stop file watchers.

## Success Criteria

- [ ] Conversation messages (user, assistant, toolResult) are automatically chunked, embedded, and stored within 500ms of `message_end`
- [ ] Codebase files in the current working directory are indexed within 30 seconds of `session_start`
- [ ] File changes are reflected in the index within 60 seconds of modification
- [ ] `huginn_memory_search` returns relevant conversation memories across all projects and codebase chunks scoped to current project by default
- [ ] Auto-retrieval prefetches results before every assistant turn without blocking the UI
- [ ] Zero external API calls during normal operation after initial download
- [ ] `node-gyp` build failure for tree-sitter does not prevent huginn from working (falls back to JS chunking for code files)

## Scope & Boundaries

**In scope:**
- Auto-ingestion of conversation messages and tool results
- Background indexing of current project source files
- Vector semantic search via `huginn_memory_search` tool
- Auto-retrieval (prefetch + context injection)
- Embedding model management and reindexing

**Out of scope:**
- Manual memory CRUD tool (no `memory` add/remove/replace tool)
- Session search tool (`session_search` stays in pi-hermes-memory if needed)
- Skill injection, correction detection, background learning loops
- Document ingestion pipeline for arbitrary documents (use RAG MCP server)
- Migration from pi-hermes-memory SQLite database (v1)
- Multi-project codebase search by default (codebase is project-scoped)

## Implementation Notes

- **Ingestion hook:** `message_end` (not `turn_end`) is the correct event for both ingestion and prefetch. `turn_end` fires after tool call batches, introducing unnecessary duplication.
- **Ingestion roles:** Default `ingestRoles` is `['user', 'assistant', 'toolResult']`. Tool results carry context-dense content that improves retrieval.
- **Schema:** Unified `huginn_chunks` table with `source_type` discriminator. No separate tables for conversation vs codebase.
- **Cross-project search scope:** `huginn_memory_search` defaults to conversation chunks from all projects + codebase chunks from the current project only. Explicit `project` or `source_type` overrides are supported.
- **Chunking strategy:** Tree-sitter AST-aware chunking for codebase source files; lightweight pure-JS chunking for conversation messages. Tree-sitter is optional — failure degrades gracefully.
- **Legacy migration:** No `/huginn-import-legacy` command. Huginn starts empty and accumulates memory organically. Pi-hermes-memory data is not imported.
- **Manual index command:** No `/huginn-index-project` command. Automatic background indexing on `session_start` with periodic re-scan covers all indexing needs without a manual trigger.
- **Background indexing latency:** Phase 3 (automated codebase indexing) is retained. Content-hash dedup means only changed/new files are re-embedded after the first run. A configurable `maxIndexedFiles` cap (default 200) and async non-blocking execution ensure first-run CPU cost does not impact the user experience.

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| `@huggingface/transformers` model download fails or is slow | Cache model in `~/.cache/huggingface`; warn user on first run; allow pre-download via config |
| `node-gyp` build failure for tree-sitter on ARM/Windows | Graceful fallback to lightweight JS chunking for code files; tree-sitter is optional |
| PGlite database corruption on crash | File-backed DB in `~/.pi/agent/huginn/db/`; rely on PGlite's WAL and occasional `.backup` |
| Embedding all codebase files on session_start is slow | Use `git ls-files` for fast enumeration; skip unchanged files via `file_mtime` comparison |
| Large files (>1MB) or minified bundles blow up index | Hardcoded exclusion rules; file size cap in scanner |
| Tool name collision with `pi-hermes-memory` | Document that user must uninstall `pi-hermes-memory`; huginn is the replacement |
| Background indexing consumes CPU during active work | Lower embedding batch priority; skip if agent is actively streaming (check `ctx.signal`) |

## High-Level Guidance

- **Extension pattern:** Follow the spec-pipeline extension's directory structure (`index.ts`, `types.ts`, `config.ts`, handlers in `handlers/`, tools in `tools/`, store in `store/`)
- **Error isolation:** All async handlers (ingestion, prefetch, indexing) must catch and log errors; never throw into pi's event loop
- **Batching:** Embed chunks in batches (default 32) to amortize ONNX inference overhead
- **Schema evolution:** Use `IF NOT EXISTS` for all DDL. Future schema changes should go through a migration helper in `store/db.ts`

## Schema

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE IF NOT EXISTS huginn_config (
  id               INT PRIMARY KEY DEFAULT 1 CHECK (id = 1),
  embedding_model  TEXT NOT NULL,
  embedding_dim    INT  NOT NULL,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS huginn_chunks (
  id            BIGSERIAL PRIMARY KEY,
  source_type   TEXT NOT NULL CHECK (source_type IN ('conversation', 'codebase')),
  session_id    TEXT,                          -- nullable: populated for conversations
  role          TEXT CHECK (role IN ('user', 'assistant', 'toolResult')), -- nullable: only conversations
  chunk_index   INT NOT NULL,
  content       TEXT NOT NULL,
  content_hash  TEXT NOT NULL,                 -- SHA-256; not globally unique
  source_file   TEXT,                          -- codebase provenance
  start_line    INT,
  end_line      INT,
  file_mtime    TIMESTAMPTZ,                   -- for invalidation
  file_size     INT,
  model_name    TEXT NOT NULL,
  embedding     vector(768),
  project       TEXT,
  metadata      JSONB NOT NULL DEFAULT '{}',
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),

  -- Dedup: same chunk content in same session (conversation)
  UNIQUE (session_id, content_hash, chunk_index),

  CHECK (
    (source_type = 'conversation' AND role IS NOT NULL)
    OR (source_type = 'codebase' AND role IS NULL)
  )
);

CREATE INDEX IF NOT EXISTS huginn_chunks_embedding_idx
  ON huginn_chunks USING hnsw (embedding vector_cosine_ops);

CREATE INDEX IF NOT EXISTS huginn_chunks_project_idx
  ON huginn_chunks (project, source_type);
```

## What Huginn Is NOT

- Not a manual memory store — no `memory` add/replace/remove tool
- Not a session search tool — no `session_search`
- Not a skill injection system — no `skill` tool
- Not a document ingestion pipeline for arbitrary files — use the Rust RAG MCP server for that
- Not dependent on a running Postgres server or external API
